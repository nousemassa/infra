# Контракт нового проекта

Восемь правил обвязки и то, чем каждое проверяется. Правило без проверки — пожелание, поэтому у каждого
назван способ проверки: команда, сторож или место в реестре.

## Правила

1. **Своя папка и свой композ со своим `name:`.** Сеть — ВЕНДОРСКАЯ (`external: true`): её создаёт стек
   вендора, и «своя» сеть молча оставила бы проект без соседей.
2. **Свой пакет с именем `<проект>_agent`.** Общее — только из `agent_core`. Граница проверяется в ОБЕ
   стороны: пакет проекта не импортирует другой проект, а общий слой не импортирует проекты.
3. **Своё окружение.** Адреса служб и `SESSIONS_DIR` задаются **явно** в композе и лончере: значения для
   контейнера и хоста разные, и «взять из общего `.env`» даёт молчаливую поломку.
4. **Пути к данным — настройкой, а не от расположения кода.** `Path(__file__).parents[N]` для данных
   запрещён: после переезда модуля такой путь указывает внутрь `site-packages`, и бот молча не
   подключается при зелёных тестах и `healthy` контейнерах.
5. **Свой лончер (`up`/`status`/`stop`), `Makefile`, `README`.** Порты публикуются **только на
   `127.0.0.1`**; у служб — `restart: unless-stopped` и `mem_limit`. Откат — `stop`, **никогда** `down` и
   не `--remove-orphans` (это снесло бы службы соседних проектов и данные).
6. **Строка в реестре `infra/compose-projects.tsv`.** Одна строка — и сторож, проверка дрейфа, ребут-чек и
   гейты видят проект сами, без правок в четырёх местах.
7. **Том с данными обязан иметь ЯВНОЕ `name:` — тогда имя проекта compose можно менять.**
   Том, объявленный без `name:`, получает префикс проекта; переименование проекта создаёт НОВЫЙ ПУСТОЙ
   том, а данные остаются в старом — так молча «теряются» корпус RAG, чекпойнты графа и общая база.
   Имя тома задаётся по РОЛИ (`shared-db-data`, `corpus-data`, `checkpoints-data`, `search-cache`) и не
   содержит имени проекта или вендора. Порядок переименования: свежий дамп → учение восстановления →
   копия тома → явные `name:` → переименование → сверка счётчиками.
8. **Зависимости — по разбору импортов**, неиспользуемые не объявлять. Общий слой подключается
   **колёсом**; порядок «`core` → колёсо → образы» держится тем, что образы собираются после колёса.

## Имена: наша операция и вендор — разные вещи

**Имя вендора остаётся только у артефакта самого вендора:** клон его дерева, его собственный `.env`, его
патчи, адаптер под него, его UI. Наши операции называются ФУНКЦИЕЙ, а вендор — их ПАРАМЕТР: `vendor-stack.sh
up` (вендор из `PLATFORM_VENDOR` или `VENDOR=…`), `vendor_capability <вендор> <возможность>`,
`lib/vendor-probes/<вендор>.sh`, `vendor-compose/<вендор>.yml`. Возможности вендора — данные в
`infra/vendors.tsv`, поэтому ветвления по имени вендора в наших скриптах нет.

**Правило одинаково для всех вендоров из `vendors.tsv`.** Ни один вендор не «основной»: сторож спрашивает
возможность (`runtime`, `http_api`, `telemetry_receiver`), проба наблюдаемости берётся по имени вендора, а
новый вендор добавляется строкой в таблицу и файлом пробы — без правок наших скриптов. В имени нашего
артефакта (пакет, том, служба, переменная обвязки) имени вендора быть не должно.

## Где живёт настройка: ОБЩАЯ ОСНОВА + ДОПОЛНЕНИЯ ПРОЕКТА

Правило у этого разделения одно: **у каждого ключа ОДИН владелец.**

* **Общая основа — `.env` в корне воркспейса.** Там ключи с ДВУМЯ и более потребителями (включая обвязку):
  адреса баз (`BRIDGE_DB_URL`, `VECTOR_DB_URL`, `REMINDERS_CHECKPOINT_DSN`), `BRIDGE_API_KEY` (мост, новости,
  сторож), `UI_SECRET`, `TELEGRAM_API_ID/HASH` и прокси MTProto, `TELEGRAM_OWNER_CHAT_ID`,
  `TELEGRAM_NEWS_BOT_TOKEN` (его читает и сторож новостей), `VISIT_REMINDER_ENABLED` (его читает и сторож
  графа), `OTEL_ENDPOINT`, ключи облачных моделей (`OPENAI_*`, `ROUTERAI_*`), контракт платформы
  (`PLATFORM_API_URL/KEY`, `PLATFORM_PROJECT_ID`, `PLATFORM_VENDOR`) и все ключи САМОГО стека вендора
  (`AGENTA_AUTH_KEY`, `CRYPT_KEY`, `RUNNER_*`, `*_IMAGE_TAG`, `REDACTION_*`, `GATEWAYS_*`) — их читает стек
  вендора, который поднимается из воркспейса.
* **Дополнения проекта — `<проект>/.env`:** `realty/.env` (токен клиентского бота, календарь, лестница
  решений, `GRAPH_DB_PASSWORD`, `MCP_*`, `JEV_*`, идентификаторы агентов диалога и объявлений),
  `news/.env` (токен бота новостей, канал, `NEWS_*`, `TEAM_*`, `OTEL_NEWS_*`, роли команды),
  `models/.env` (`EMBED_MODEL_FILE`, `LLAMA_KEYS_FILE`), `search/.env` (`SEARXNG_SECRET`).
* **Адреса локальных сервисов моделей — у агента, не в основе.** `LLAMA_EMBED_URL`, `SOLVER_URL` и их
  ключи живут в `.env` продукта (плюс `*_URL_HOST` — адрес для хостового лончера): службы локальные, но в
  бою могут стоять на разных хостах, поэтому адрес — свойство развёртывания. Ядро (`agent_core`) адресов
  моделей не знает вовсе.
* **Спорный ключ НЕ копируется.** Если ключ понадобился второму потребителю — он переезжает в основу, а не
  дублируется: копия разъезжается молча (версия совпала, содержимое — нет).
* **Как это получают потребители:** контейнер — `env_file: [../.env, ./.env]` в композе (проект читается
  вторым и перекрывает основу); хостовый процесс — `AGENT_ENV_FILES="$WORKSPACE/.env:$PROJECT_DIR/.env"`
  (общий слой читает список файлов); сторож — читает ТОЛЬКО основу, поэтому его ключ обязан жить в основе
  (иначе сторож молча не увидит настройку).

## Если у проекта есть службы: наблюдение

Служба без сторожа — служба, о падении которой узнают от клиента. Поэтому вместе с проектом:

* **сторож** в `infra/health/health-<проект или служба>.sh` — по образцу соседей: причина в тексте,
  `GUARD_PROJECT`/`GUARD_SERVICE` (первая пара — **в начале строки**: её читает проверка реестра),
  алерт владельцу через `POST /api/ops/alert`, лечение через `infra/lib/service_guard.sh`;
* **юнит-пара** `infra/systemd/bridge-<проект>-health.{service,timer}` с `Environment=AGENT_WORKSPACE=…`
  (без неё сторож не найдёт воркспейс);
* **строка в списке включения** `infra/systemd/install.sh` — список перечислен ЯВНО, и юнит, которого там
  нет, не включится;
* **имя в списке** `infra/checks/reboot-roundtrip.sh` — он перечисляет сторожей поимённо.

## Чек-лист (то же самое, но выполнимо)

```bash
# 1. Композ разбирается и называет себя
docker compose -f <проект>/compose.<проект>.yaml config -q
# 3-5. Адреса и порты заданы в лончере и композе явно, порты — на loopback
grep -n "127.0.0.1" <проект>/compose.<проект>.yaml <проект>/*-up.sh
# 6. Реестр
grep -n "<имя проекта>" infra/compose-projects.tsv              # строка есть (одна!)
# 7. Тома (если есть)
docker volume ls | grep <имя проекта>                           # тома названы ожидаемо
# Наблюдение
make -C infra check                                             # пути в юнитах сходятся с фактом
make -C infra health                                            # все сторожа ok (включая нового)
```

## Чего контракт НЕ требует

* **Не требовать своего образа**: проекту-обвязке (как `search/`) достаточно образов вендора и конфига.
* **Не требовать своего сторожа на каждую службу**: если службы работают только вместе (движок и его
  обёртка), сторож ОДИН, а причина в тексте называет, что именно упало.
* **Не копировать обвязку к себе**: юниты, сторожа и дампы — общие, в `infra/`.
